# ADR-019.2: Closed-Loop Feedback Fabric

## Status

Accepted for Phase 19.2 implementation.

## Context

Phase 19.1 shipped the canonical `IntelligenceItem` contract, viewer preference mapping, and mobile member-feed parity. Phase 19.2 is a data collection phase for authenticated member interactions with intelligence-ranked content. It must not change ranking, scoring, ordering, candidate generation, or enable dark engines.

Existing Prisma schema already includes `reco_feedback_log` with a JSON metadata column. Current recommendation and discovery code reads specific legacy actions such as `hide`, `dismiss`, `report`, `follow`, and `click`, and also reads `reco_impression_log` for frequency and report-rate behavior. Writing normal production action names or impression aggregates from this phase could change live ranking behavior.

## Decision

Create a reusable Enterprise Intelligence Feedback Fabric with modular backend components:

- `FeedbackEvent`
- `FeedbackCollector`
- `FeedbackNormalizer`
- `FeedbackValidator`
- `FeedbackStorage`
- `FeedbackMetrics`
- `FeedbackReplay` as a future-ready concept only

The backend stores Phase 19.2 feedback in `reco_feedback_log` using namespaced `iff_*` actions, such as `iff_impression`, `iff_apply`, and `iff_not_interested`. The fabric does not write to `reco_impression_log`, does not invalidate recommendation caches, and does not call Discovery Engine, Enterprise Search, Notification Intelligence, Scrolitha, vector, or embedding services.

The frontend adds a reusable collector service and passively records member-feed page impressions from authenticated orchestrated feed responses. Collection is fire-and-forget and does not block rendering or change UI behavior.

## Data Flow

1. Authenticated member requests an orchestrated member feed.
2. The frontend receives ordered `IntelligenceItem` content exactly as produced by the backend.
3. The frontend collector builds bounded feedback events with entity id, entity type, action, feed position, session id, device type, feed mode, intelligence version, reason codes, timestamp, and source surface.
4. Events are submitted to `POST /api/intelligence/feedback/events`.
5. The route requires existing authentication and applies HTTP and service-level rate limits.
6. The service validates and normalizes every event.
7. Storage writes accepted events to `reco_feedback_log` with namespaced actions and safe metadata.
8. In-process aggregate counters track received, accepted, rejected, duplicate, source, type, entity, validation failure, and processing latency totals.

## Privacy

The fabric stores only interaction metadata needed for future intelligence analysis. It does not store raw page content, post bodies, message contents, private files, moderation evidence, vectors, embeddings, scores, weights, or candidate generation details. Metadata is whitelisted and bounded.

## Security

The write endpoint is authenticated. Batch size is capped. Events are rate-limited per viewer and via route-level HTTP limiting. Event identifiers are hashed into deterministic storage ids for idempotency. Logs and metrics avoid PII and do not emit user ids, content, or private payload values.

## Database Impact

No schema change is required. Phase 19.2 reuses `reco_feedback_log` and stores namespaced actions to avoid changing existing ranking readers. `reco_impression_log` is intentionally not used because it participates in existing frequency and report-rate calculations.

## Future Integration

Future Enterprise Intelligence phases can consume the namespaced feedback stream through backend services for admin summaries, trends, top reasons, dismiss reasons, and engagement analysis. Any future use in ranking, scoring, search, notifications, vectors, embeddings, or Scrolitha requires a separate explicit phase and rollout gate.
