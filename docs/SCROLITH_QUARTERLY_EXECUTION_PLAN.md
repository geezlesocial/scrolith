# Scrolith Quarter-by-Quarter Execution Plan

## 1. Planning Horizon

This plan converts the implementation backlog into a 12-month execution schedule.

It assumes:

- one product roadmap
- shared frontend/backend/mobile delivery
- admin control must ship alongside major features
- reliability work must lead feature expansion

The plan is organized into four quarters:

- Q1: trust and reliability foundation
- Q2: commerce conversion and creator monetization
- Q3: professional publishing, enterprise workflow, and AI acceleration
- Q4: scale, experimentation, and defensibility

## 2. Strategic Goal by Quarter

### Q1 goal

Make Scrolith trustworthy, stable, and conversion-ready.

### Q2 goal

Turn content, profiles, and conversations into measurable commerce flows.

### Q3 goal

Differentiate through professional publishing, enterprise hiring, and AI-assisted workflows.

### Q4 goal

Strengthen scale, governance, experimentation, and long-term platform moat.

## 3. Q1 Execution Plan

## Theme

Trust, reliability, and first conversion loop.

## Main outcomes

- users trust profiles and counterparties more
- live and social actions fail less
- messaging can begin a real business workflow
- profiles can become storefront-ready surfaces
- Scroll comments become publicly social and useful

## Features

### Trust and reliability

- Role-based verification badges
- Delivery and reliability score
- Verified portfolio proof system
- Live observability and diagnostics
- Retry-safe reactions, comments, and writes
- Media upload resilience

### Conversion flow

- Convert chat thread to brief
- Convert brief to proposal
- Storefront tab on profiles
- Public threaded Scroll comments and replies

## Deliverables

- public trust indicators on profile and content surfaces
- admin verification review flow
- traceable live session health dashboard
- duplicate-write prevention for reactions and comments
- message-to-brief entry point
- brief-to-proposal linkage
- profile storefront shell
- public Scroll comment thread

## Exit criteria

- trust indicators are visible and governable
- social write actions are idempotent
- live incidents are traceable
- users can move from chat to brief to proposal
- storefront tab is visible on eligible profiles
- Scroll comments and replies work publicly

## 4. Q2 Execution Plan

## Theme

Creator commerce and transaction acceleration.

## Main outcomes

- profiles and media become commerce surfaces
- repost and share create measurable demand
- affiliate commerce begins
- live starts to function as a transaction surface
- subscriptions add recurring revenue

## Features

- Convert proposal to contract
- Timeline inside messaging
- Tag products and services in content
- Pinned offers and featured collections
- Repost with commentary
- Share cards with attribution tracking
- Seller affiliate campaign creation
- Creator affiliate discovery
- Paid memberships
- Subscriber-only content gates
- Scroll product and service tags
- Pinned live offers
- Co-host and guest request system

## Deliverables

- contract conversion path from proposal
- commerce-aware message timeline
- tagging engine for posts, Scroll, and LIVE
- storefront merchandising controls
- share attribution model
- seller-side affiliate campaign setup
- creator campaign discovery
- membership checkout and gating
- live pinned offers and guest queue

## Exit criteria

- proposal-to-contract conversion is usable in production
- content tags create measurable downstream actions
- affiliate campaigns can be created and joined
- creator subscriptions work with gated content
- live offers and co-hosting do not destabilize viewing

## 8. Quarterly Risk Watch

### Q1 risks

- trust model gets overcomplicated
- reliability work gets deferred behind feature pressure

### Q2 risks

- storefront and content tagging ship without moderation controls
- affiliate and subscription logic ship without payout safety

### Q3 risks

- AI features expand faster than quality controls
- enterprise workspaces ship without permission maturity

### Q4 risks

- experimentation engine ships before analytics quality is strong enough
- policy engine becomes too broad without clear scope

## 9. Operating Rule

No quarter should close with user-facing features shipped without:

- admin controls
- analytics instrumentation
- QA coverage
- rollback or disable path

## 10. Final Planning Principle

If a quarterly feature does not strengthen one of these loops, it should be reconsidered:

- identity to opportunity
- audience to revenue
- message to money
- social proof to commerce
- admin to platform quality
