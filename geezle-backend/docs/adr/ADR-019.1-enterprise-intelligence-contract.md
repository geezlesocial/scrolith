# ADR-019.1 — Enterprise Intelligence Contract, Preference Unification, Mobile Feed Parity

## Status
Accepted for Phase 19.1 (implementation complete; not production-enabled as a dark engine).

## Context
Phase 18 delivered presentation-only feed intelligence chips. Ranking metadata, recommendation reasons, Insights feed-focus modes, and Member Home intent modes evolved as parallel vocabularies. Mobile authenticated feed still used community-feed transport while desktop Member Home already preferred `GET /discovery/v2/member-feed`.

## Decision

### 1. Canonical intelligence envelope
Additive, versioned contract (`intelligenceVersion: 19.1.0`) normalized server-side:

- `entityType`, `entityId`
- `score`, `rankMode`, `recipeKey`
- `primaryReason`, `reasons`, `reasonCodes`
- `confidence`, `policyTags`, `experimentArm`

Attached to orchestrated member-feed items without changing sort order, candidate generation, or ranking weights.

### 2. Reason-code policy
Controlled catalog grounded in existing ranking text/signals (e.g. `TOPIC_AFFINITY`, `HIRING_INTENT`, `SPONSORED`).
Client-safe labels only. No free-form model-generated ranking explanations in this phase.
Raw vectors, embeddings, feature weights, moderation evidence, and private signals are never serialized.

### 3. Privacy boundary
- Client receives short human reasons and stable reason codes only.
- Invalid scores become `null` (never `NaN` / `Infinity`).
- Object-coercion artifacts (`[object Object]`) are rejected.

### 4. Preference mapping
| Insights mode | Member feed intent | Notes |
|---------------|--------------------|-------|
| growth | for_you | Default personalization |
| opportunity | hire or sell | Role-aware: employer→hire, freelancer→sell |
| network | following | Following is a supported feed mode |
| learning | learn | Direct map |

Reverse map keeps surface-specific labels. `local` remains a specialized feed intent; Insights maps it to `growth` because Insights has no local mode.

Persistence reuses existing `FeedModePreference` (Insights). No schema migration. GET/POST `/insights/feed-mode` responses gain additive fields: `feedIntent`, `mapped`, `version`, `personalizationEnabled`.

### 5. Server-owned ranking
Frontend does not invent ranking scores. Presentation prefers server `intelligence` / `ranking` reasons. Generic chips remain fallback only.

### 6. Mobile primary/fallback transport
Authenticated mobile feed:

1. Try `GET /discovery/v2/member-feed` with normalized intent.
2. Preserve opaque cursor + feedKey semantics from orchestrator.
3. On soft failure (timeout, 5xx, empty unusable page) fall back to existing community feed path.
4. 401/403 are not hidden as ordinary fallback when `hardFailAuth` is set.

### 7. Engine independence
No enablement of:

- `DISCOVERY_ENGINE_*`
- `ENTERPRISE_SEARCH_*`
- `NOTIF_INTEL_*`
- Scrolitha in the synchronous ranking path
- vectors / embeddings / Redis

### 8. Rollback
- Frontend: remove mobile orchestrator-first branch; chips still work on legacy payloads.
- Backend: stop attaching `intelligence` envelope; existing `why` / `ranking` fields remain.
- Preference additive fields are ignore-safe for older clients.

## Consequences
- Consistent explainability path across desktop and mobile.
- Preference surfaces can converge without migration.
- Phase 19.2+ can plug Discovery Engine / Search reasons into the same envelope when flags are intentionally enabled.
